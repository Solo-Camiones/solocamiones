## Objetivo

Toda acción principal de listado/detalle responde de inmediato y con el mismo patrón: carga, éxito, error, vacío. Sin rediseñar pantallas.

## Qué se entregó

### Loading

- `Skeleton` con bloques `animate-pulse`, `role="status"`, `aria-busy` y región `aria-live="polite"` (texto `sr-only` para lectores de pantalla).
- Sustituye el párrafo “Cargando …” en Dashboard, Inventario, Ventas, Órdenes, Rentabilidad, Clientes, Usuarios, Catálogos y cola/detalle del mecánico. El mecánico usa bloques más altos (`size="lg"`).
- `Button` acepta `busy`: deshabilita y pone `aria-busy`. Cableado mínimo en Login, pie de Registrar, Confirmar venta (POS) y Completar del mecánico.

### Success

Los toasts de perfil, catálogos y clientes ya existían (`Perfil actualizado`, `Cliente creado` / `Cliente actualizado`, categoría/servicio). El diálogo post-registro de pieza no se duplica.

### Error

`toPageLoadMessage` reemplaza cuerpos que parecen estado HTTP (`HTTP 500`, `Error 500`) por “No pudimos cargar …”. Los mensajes de negocio (permisos, validación) se muestran igual. El mecánico y el POS siguen usando `toMechanicUserMessage` / `toPosUserMessage`.

### Empty

Títulos ya específicos se mantienen. `WorkOrderTable` y `SalesTable` (sin búsqueda) usan títulos de vista/pestaña, no “No hay registros.”. El CTA de inventario sigue en el encabezado.

## Cómo verificar

```bash
npm run test:unit -w @solocamiones/web -- tests/unit/shared/ui/page-load-message.test.ts
npm run test:component -w @solocamiones/web -- tests/component/shared/Skeleton.test.tsx tests/component/shared/Button.test.tsx tests/component/inventory/InventoryPage.test.tsx tests/component/dashboard/DashboardPage.test.tsx tests/component/mechanic/MechanicPages.test.tsx
```

Manual: abrir Inventario/Inicio y ver el skeleton (no un párrafo “Cargando …”); forzar un fallo HTTP y leer “No pudimos cargar …”; guardar un cliente y ver toast; Completar/Confirmar venta/Login con `aria-busy` al enviar.
