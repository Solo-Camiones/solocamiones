# Plan de Mejora UX/UI — Solo Camiones

## Objetivo general

Realizar un proceso de **UX Hardening** sobre el frontend actual de Solo Camiones sin rediseñar completamente la aplicación ni alterar reglas de negocio existentes.

El propósito es mejorar:

- Facilidad de uso.
- Claridad visual.
- Consistencia.
- Prevención de errores.
- Velocidad de operación.
- Accesibilidad.
- Experiencia responsive.
- Cumplimiento de la documentación funcional del proyecto.

La documentación debe mantenerse como **fuente de verdad**. La interfaz debe adaptarse a las reglas definidas en:

- `docs/FEATURES`
- `ROLES_AND_PERMISSIONS.md`
- `USE_CASE_FLOWS.md`
- `PROTOTYPE_PLAN.md`

---

# Milestone 1 — Integridad funcional y consistencia con documentación

## Objetivo

Asegurar que ninguna pantalla permita acciones o entrada de datos que contradigan las reglas documentadas del sistema.

## Problemática

El caso más importante identificado se encuentra en el registro de atributos de inventario.

Actualmente el usuario puede introducir atributos manualmente como texto libre, aunque la documentación establece que los atributos deben depender de la categoría seleccionada.

Esto puede provocar inconsistencias como:

```text
Voltaje: 24V
voltaje: 24 v
Volt: 24
V: 24V
```

Aunque todos representan el mismo concepto, el sistema los puede terminar tratando como valores diferentes.

## Impacto

Esto afecta directamente:

- Consistencia de los datos.
- Calidad de las búsquedas.
- Filtrado.
- Reportes.
- Mantenimiento futuro.
- Integraciones.
- Experiencia de usuario.

También obliga al usuario a recordar cómo debe escribir cada atributo.

## Solución propuesta

### 1.1 Atributos dinámicos por categoría

Modificar el registro de inventario para que:

1. El usuario seleccione una categoría.
2. El frontend obtenga los atributos definidos para esa categoría.
3. Se generen automáticamente los campos necesarios.
4. Cada atributo tenga su validación correspondiente.

Ejemplo:

### Categoría: Batería

- Voltaje.
- Capacidad.
- Marca.

### Categoría: Goma

- Ancho.
- Perfil.
- Rin.
- Marca.

Eliminar el textarea actual de atributos libres.

### 1.2 Revisar reglas funcionales pantalla por pantalla

Cruzar cada feature del frontend con:

- `docs/FEATURES`
- `ROLES_AND_PERMISSIONS.md`
- `USE_CASE_FLOWS.md`

Revisar especialmente:

- Inventario.
- Facturación.
- Desmonte.
- Órdenes de trabajo.
- Categorías.
- Reembolsos.
- Reservas.
- Ubicaciones.
- Estados.

## Criterios de aceptación

- No se pueden crear atributos arbitrarios.
- La categoría determina qué atributos aparecen.
- Cada atributo tiene validación.
- Ninguna acción visible viola permisos del usuario.
- La UI coincide con la documentación funcional.

## Prioridad

**P0 — imprescindible antes de producción.**

# Milestone 2 — Simplificar la lectura del inventario

## Objetivo

Permitir que una persona encuentre y entienda una pieza rápidamente, incluso cuando existan cientos o miles de registros.

## Problemática

Actualmente la información mostrada es correcta, pero demasiados conceptos aparecen agrupados visualmente.

Una pieza puede mostrar simultáneamente:

- Disponible.
- Instalada.
- Reservada.
- Incompleta.
- No desmontar.
- Protegida.
- Stock.

El usuario termina leyendo demasiada información para responder preguntas simples como:

> ¿Esta pieza está disponible y dónde está?

## Impacto

- Mayor carga cognitiva.
- Lectura más lenta.
- Más probabilidad de interpretar incorrectamente un estado.
- Menor eficiencia en inventario.
- Mayor curva de aprendizaje para usuarios nuevos.

## Solución propuesta

### 2.1 Reorganizar la tabla de inventario

Pasar de una estructura similar a:

| Nombre | Categoría | Ubicación | Estado |
| ------ | --------- | --------- | ------ |

a:

| Pieza | Categoría | Ubicación | Disponibilidad | Relación | Alertas |
| ----- | --------- | --------- | -------------- | -------- | ------- |

Ejemplo:

| Alternador Bosch | Alternador | Patio A | Disponible | Motor MOT-0021 | Reservado |

### 2.2 Definir jerarquía visual

Estados normales deben tener menor peso visual:

- Disponible.
- Instalado.
- Independiente.

Las excepciones deben destacar más:

- Reservado.
- No desmontar.
- Incompleto.
- Sin ubicación.

### 2.3 Mejorar términos ambiguos

Cambiar:

```text
Pendiente
```

por términos más específicos como:

```text
Ubicación pendiente
```

o:

```text
Sin ubicación registrada
```

## Criterios de aceptación

Desde la tabla, el usuario debe poder identificar rápidamente:

1. Qué es la pieza.
2. Dónde está.
3. Si puede venderse.
4. Si pertenece a un ensamblaje.
5. Si existe alguna restricción.

## Prioridad

**P1 — alta.**

# Milestone 3 — Búsqueda y filtros operacionales

## Objetivo

Reducir el tiempo necesario para encontrar piezas y productos.

## Problemática

La búsqueda actual funciona, pero el dominio del sistema permite múltiples estados y situaciones operacionales que necesitan consultas frecuentes.

## Impacto

Sin filtros adecuados, el usuario puede tener que:

- Revisar demasiados resultados.
- Abrir piezas individualmente.
- Repetir búsquedas.
- Perder tiempo durante una venta.
- Cometer errores al elegir inventario.

## Solución propuesta

### 3.1 Agregar filtros rápidos

Incluir accesos directos para:

- Disponible.
- Instalado.
- Independiente.
- Reservado.
- Ensamblajes.
- Incompletos.
- Por cantidad.

### 3.2 Agregar filtros avanzados

Dentro de una opción **Más filtros** incluir:

- Categoría.
- Ubicación.
- Condición.
- Estado comercial.
- Vendidos.
- Tipo de inventario.

### 3.3 Mostrar filtros activos

Ejemplo:

```text
Filtros activos: Motores ×  Disponible ×
Limpiar filtros
```

## Consideración UX

No mostrar todos los filtros simultáneamente.

Los filtros frecuentes deben estar visibles y los avanzados deben mantenerse dentro de un panel secundario.

## Criterios de aceptación

Un vendedor debe poder encontrar rápidamente consultas como:

> Alternadores disponibles, independientes y ubicados en almacén.

sin navegar por múltiples pantallas.

## Prioridad

**P1.**

# Milestone 4 — Mejorar el registro de inventario

## Objetivo

Hacer el formulario más claro, corto y difícil de completar incorrectamente.

---

## 4.1 Eliminar scroll interno innecesario

### Problemática

Existe riesgo de tener múltiples niveles de scroll dentro del modal.

### Impacto

- Confusión.
- Botones fuera de la vista.
- Mala experiencia en pantallas pequeñas.
- Sensación de formulario pesado.

### Solución

Mantener un único responsable del scroll, preferiblemente el contenido principal del modal.

---

## 4.2 Footer de acciones visible

Mantener visibles durante formularios largos:

```text
Cancelar                         Registrar
```

Esto evita que el usuario tenga que desplazarse completamente al final para confirmar.

---

## 4.3 Código generado automáticamente

### Problemática

El código interno aparece como un input deshabilitado.

Esto puede dar la impresión de que el usuario debería poder modificarlo.

### Solución

Mostrarlo como información del sistema:

```text
Código interno

Se generará automáticamente al registrar.
```

Después del registro:

```text
MOT-000042
```

---

## 4.4 CTA contextual

Actualmente se utiliza un texto como:

```text
Ver pieza
```

incluso cuando se registra un producto por cantidad.

Cambiar según el modo:

### Individual

```text
Ver pieza
```

### Cantidad

```text
Ver producto
```

---

## 4.5 Agrupar visualmente el formulario

Separar el registro en secciones:

### Identificación

- Nombre.
- Categoría.
- Marca.

### Inventario

- Tipo.
- Cantidad.
- Ubicación.

### Características

- Atributos dinámicos.

### Evidencia

- Fotos.

## 4.6 Proteger información sin guardar

Si el formulario contiene cambios, `Escape`, el backdrop, la X y **Cancelar** deben pedir
confirmación antes de descartarlos. Mientras el registro se guarda, ninguna vía de cierre debe
interrumpir la respuesta de la operación.

## Criterios de aceptación

Una persona nueva debe poder registrar un artículo sin necesitar explicación constante de cada campo.

## Prioridad

**P1.**

# Milestone 5 — Dashboard orientado a acciones

## Objetivo

Convertir el dashboard de una colección de números en una pantalla para tomar decisiones.

## Problemática

Actualmente indicadores informativos y problemas urgentes pueden tener pesos visuales similares.

Ejemplo:

```text
Facturas hoy: 8
```

y:

```text
Componentes por validar: 4
```

no tienen la misma importancia operacional.

## Impacto

El usuario debe analizar demasiada información antes de identificar problemas que requieren atención.

## Solución propuesta

Separar el dashboard en tres grupos.

## Necesita atención

- Componentes por validar.
- Desarmes pendientes.
- Tasas de cambio pendientes.
- Ensamblajes incompletos.

## Operación de hoy

- Ventas.
- Facturas.
- Inventario disponible.
- Órdenes.

## Finanzas

- Saldo pendiente.
- Ganancia.
- Cobros.

---

## 5.1 KPI accionables

Los indicadores relevantes deben funcionar también como accesos directos.

Ejemplo:

```text
7 Desarmes pendientes →
```

debe llevar a algo como:

```text
/work-orders?type=DISMANTLING&status=PENDING
```

Otro ejemplo:

```text
4 Componentes por validar →
```

debe abrir directamente el listado correspondiente.

## Criterio principal

Al entrar al dashboard, el administrador debe poder responder en segundos:

> ¿Hay algo que necesita mi atención?

## Prioridad

**P1.**

# Milestone 6 — Hardening del POS y facturación

## Objetivo

Reducir errores y hacer evidente por qué una venta no puede completarse.

---

## 6.1 Explicar botones bloqueados

### Problemática

El botón de confirmar venta puede estar deshabilitado mientras la explicación se encuentra en otra sección de la pantalla.

### Impacto

El usuario puede interpretar que:

- El sistema está fallando.
- El botón no funciona.
- Falta algún permiso.
- La aplicación está congelada.

### Solución

Mostrar junto al botón:

```text
Confirmar venta
⚠️ Faltan 3 requisitos
```

o:

```text
⚠️ Seleccione cliente y complete 2 precios.
```

---

## 6.2 Navegar hacia los errores

Agregar una acción:

```text
Ver requisitos
```

que lleve al primer campo problemático.

Orden sugerido:

1. Cliente.
2. Precio.
3. Moneda.
4. Información fiscal.
5. Otros bloqueos.

---

## 6.3 Deshacer al quitar productos

No utilizar modales de confirmación para eliminar una línea del POS.

En su lugar:

```text
Producto eliminado. Deshacer
```

durante unos segundos.

Esto mantiene rapidez sin sacrificar control.

---

## 6.4 Responsive de líneas

### Desktop

Mantener la tabla actual.

### Tablet / móvil

Convertir líneas en tarjetas:

```text
Alternador Bosch
Pieza · MOT-0021

Cantidad: 1
Precio: RD$14,000
ITBIS: RD$2,135
Total: RD$14,000

Quitar
```

## Prioridad

**P1 / P2.**

# Milestone 7 — Órdenes de trabajo y experiencia del mecánico

## Objetivo

Mantener la buena experiencia actual y corregir estados límite.

La interfaz del mecánico ya está bien adaptada al tipo de usuario, por lo que los cambios deben ser mínimos.

---

## 7.1 Manejar órdenes canceladas

### Problemática

Una orden cancelada podría terminar pasando filtros generales sin pertenecer a ninguna sección visible.

### Soluciones posibles

#### Opción A

Las órdenes canceladas dejan de aparecer al mecánico.

#### Opción B

Crear una sección:

```text
Historial
```

con:

- Completadas.
- Canceladas.

La decisión debe corresponder con las reglas funcionales del proyecto.

---

## 7.2 Reutilizar el patrón de bloqueo existente

La pantalla del mecánico ya utiliza correctamente:

```text
Completar
```

deshabilitado y una explicación inmediata como:

```text
Falta evidencia antes y después.
```

Este mismo patrón debe reutilizarse en otras áreas del sistema, especialmente POS y formularios.

## Prioridad

**P1.**

---

# Milestone 8 — Lenguaje y consistencia del producto

## Objetivo

Eliminar cualquier sensación de prototipo o sistema pensado desde la perspectiva del desarrollador.

## Problemática

Existen términos técnicos o internos que pueden ser claros para desarrollo pero no para usuarios finales.

Ejemplos:

- demo.
- baseline.
- mock.
- prototype.
- nombres internos.
- códigos técnicos innecesarios.

## Solución propuesta

Cambiar términos como:

```text
Baseline incompleto
```

por:

```text
Registro inicial incompleto
```

o, mejor aún:

```text
Componentes pendientes de confirmar
```

cuando describa con mayor precisión la situación real.

---

## 8.1 Login

Eliminar placeholders como:

```text
demo1234
```

Usar:

```text
Ingrese su contraseña
```

o ningún placeholder.

---

## 8.2 Crear glosario UX

Definir nombres oficiales para conceptos frecuentes.

| Concepto                | Texto UI                 |
| ----------------------- | ------------------------ |
| Commercial availability | Disponibilidad           |
| Physical relationship   | Relación                 |
| Parent assembly         | Ensamblaje               |
| Quantity item           | Producto por cantidad    |
| Work order              | Orden de trabajo         |
| Dismantling             | Desmonte                 |
| Missing location        | Sin ubicación registrada |

Esto evita que distintas pantallas utilicen términos diferentes para el mismo concepto.

## Prioridad

**P2.**

---

# Milestone 9 — Estados globales y feedback

## Objetivo

Hacer que toda acción tenga respuesta inmediata y consistente.

## Solución propuesta

Estandarizar los siguientes estados.

### Loading

- Skeletons.
- Spinners.
- Botones con estado de carga.
- Evitar doble envío.

### Success

Ejemplo:

```text
Pieza registrada correctamente.
```

### Error

Evitar mensajes como:

```text
Error 500
```

Preferir mensajes comprensibles:

```text
No pudimos registrar la pieza.
```

Cuando sea posible, ser más específico:

```text
La ubicación seleccionada ya no está disponible.
```

### Empty states

Evitar:

```text
No hay registros.
```

Preferir:

```text
No existen órdenes pendientes.
```

Cuando corresponda, agregar una acción:

```text
Crear orden
```

## Prioridad

**P2.**

- `Tab`.

- Focus visible.
- Modales.
- Drawers.
- Contraste.

# Milestone 11 — Responsive específico por rol

## Objetivo

Diseñar la experiencia responsive según el contexto real de cada tipo de usuario.

No es necesario que todas las pantallas tengan exactamente la misma prioridad móvil.

---

## Administrador

Prioridad:

```text
Desktop → Tablet → Mobile
```

Las funciones administrativas pueden mantener mayor densidad de información.

---

## Vendedor

Prioridad:

```text
Desktop → Tablet
```

Especialmente importante para:

- POS.
- Inventario.
- Clientes.
- Facturación.

---

## Mecánico

Prioridad:

```text
Mobile → Tablet → Desktop
```

Porque su contexto de trabajo ocurre físicamente alrededor de vehículos, motores y piezas.

## Beneficio

Esto evita invertir esfuerzo excesivo en hacer una tabla administrativa perfecta a 360 px mientras se descuida la experiencia móvil que sí utiliza diariamente el mecánico.

## Prioridad

**P2.**

---

# Milestone 12 — Pruebas de usabilidad con usuarios reales

## Objetivo

Detectar problemas que no pueden identificarse únicamente revisando código o diseños.

## Participantes recomendados

Realizar pruebas con entre 3 y 5 personas similares a los usuarios finales:

- Vendedor.
- Administrador.
- Encargado de almacén.
- Mecánico.

## Metodología

No explicar inicialmente cómo utilizar la aplicación.

Dar tareas concretas como:

> Busca un alternador disponible.

> Registra esta goma.

> Vende esta pieza.

> Encuentra dónde está este motor.

> Completa esta orden de desmonte.

Observar:

- Dónde dudan.
- Dónde preguntan.
- Dónde hacen clic incorrectamente.
- Dónde retroceden.
- Qué términos no comprenden.
- Qué tareas tardan demasiado.

## Resultado esperado

Convertir los problemas observados en nuevos issues UX con:

- Problema.
- Impacto.
- Evidencia.
- Prioridad.
- Solución propuesta.

## Prioridad

**Validación final antes de considerar madura la UX.**

# Estrategia de ramas sugerida

No se recomienda realizar todos los cambios dentro de una única rama muy grande.

Una rama general podría utilizarse como referencia:

```text
chore/frontend-ux-hardening
```

Sin embargo, para facilitar revisión, testing y rollback, es preferible dividir los cambios importantes.

Ejemplos:

```text
feat/inventory-ux-hardening
feat/inventory-filters
feat/inventory-registration-ux
feat/dashboard-ux-hardening
feat/pos-ux-hardening
fix/mechanic-order-states
chore/frontend-copy-consistency
chore/frontend-accessibility
chore/frontend-responsive-hardening
```

# Regla principal durante la implementación

La UX debe adaptarse a las reglas de negocio existentes.

No se deben modificar reglas funcionales simplemente para hacer que una pantalla resulte más cómoda.

La prioridad de decisión debe mantenerse así:

```text
Documentación funcional
        ↓
Reglas de negocio
        ↓
Permisos y casos de uso
        ↓
UX/UI
        ↓
Implementación visual
```

Tampoco se recomienda refactorizar componentes que ya funcionan si el cambio no aporta directamente:

- Mayor claridad.
- Mejor accesibilidad.
- Menor carga cognitiva.
- Mayor eficiencia.
- Mejor prevención de errores.
- Mayor consistencia.

El objetivo de este plan no es hacer que la aplicación sea solamente más atractiva visualmente.

El objetivo es que cada usuario pueda identificar fácilmente:

> Qué está ocurriendo, qué puede hacer y cuál es su siguiente acción.
